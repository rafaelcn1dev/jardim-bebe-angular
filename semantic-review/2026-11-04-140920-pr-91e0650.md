# Backend de produção que persiste via commits no GitHub

A página `/baixar` precisa criar e editar sons de animais no site publicado, mas o host estático do Render não tem disco para escrita. Esta mudança adiciona um web service Node sem dependências (`server/`) que persiste os uploads fazendo commit no repositório do GitHub através da Contents API e, em seguida, aciona um Deploy Hook do Render para forçar o frontend a reconstruir com os novos assets. Enquanto o redeploy roda, o backend faz proxy de `raw.githubusercontent.com` para que os previews toquem imediatamente. O frontend ganhou um helper `sound-server.ts` que seleciona a URL base de desenvolvimento (localhost:4300) ou produção (onrender.com), e o `jardim.component.ts` agora recorre a esse servidor quando um `.mp3` empacotado está ausente.

Atenção: o serviço **não tinha autenticação e o CORS vinha com padrão `*`** (confirmado), então qualquer pessoa na internet podia disparar commits no repositório; o `/api/download` é um **fetch server-side de uma URL arbitrária — um SSRF clássico** (confirmado); e o read-modify-write do `animals.json` tem uma **corrida de lost-update / 409** sob escritas concorrentes, sem retry (confirmado).

> Nota: este documento é o registro do code review no estado original (commits 91e0650 e d8c6fc8). As correções foram aplicadas depois, no commit 39f19e7 — ver a seção "Situação após as correções" ao final.

## Visão geral

O modelo de persistência é a decisão de design central: toda escrita vira um commit no GitHub, e o commit (mais um Deploy Hook explícito) é o que propaga o conteúdo para o site publicado. É engenhoso para o plano gratuito, mas transforma cada ação do usuário em uma mutação do repositório, que é a lente por trás da maioria das preocupações abaixo.

A postura de segurança era a área mais fraca. O serviço é um proxy de escrita para um repositório Git que guarda um `GITHUB_TOKEN` com permissão de escrita em Contents, mas vinha sem autenticação e com uma origem CORS aberta por padrão. O endpoint `/api/download` fazia fetch server-side de URLs arbitrárias fornecidas por quem chama, e os sanitizadores de `copySound`/`/sounds/` mantinham `.` e `-`, deixando sequências `..` intactas.

A superfície de API espelha o servidor local de desenvolvimento para o frontend reaproveitar um único caminho de código: health, listagem, um GET de proxy "raw" e quatro POSTs de escrita. A validação de entrada é razoável nos nomes (slug NFD), mas rala no conteúdo do download/upload em si.

A concorrência não tinha proteção. O `saveAnimal` faz um read-modify-write de um único arquivo JSON chaveado pelo `sha` do blob do GitHub; duas gravações quase simultâneas perdem uma atualização ou falham com 409 que vinha à tona como um 400 genérico, sem retry.

O tratamento de erro era consistente mas grosseiro — tudo colapsava para HTTP 400 com a mensagem de erro crua, o que vazava detalhe interno e impedia o frontend de distinguir "entrada inválida" de "conflito no GitHub" ou "serviço externo fora do ar". Não havia testes automatizados para nada disso.

<details>
<summary>Problemas (9)</summary>

1. **Sem autenticação nos endpoints de escrita** — `/api/download`, `/api/upload`, `/api/copy`, `/api/animal` ficavam abertos para a internet e cada um dispara um commit com o token de escrita do servidor. Adicionar um segredo compartilhado ou checagem de token antes de qualquer escrita.
2. **CORS com padrão `*`** — `ALLOWED_ORIGIN` caía para `*` no `index.mjs`, então qualquer site podia chamar os endpoints de escrita pelo navegador. Usar como padrão a origem conhecida do frontend e falhar fechado (fail closed) se não definida em produção.
3. **SSRF em `/api/download`** — `downloadSound` fazia fetch de qualquer URL http(s) server-side com `redirect: 'follow'` e sem allowlist de host, alcançável a metadados da nuvem (169.254.169.254) e serviços internos. Impor allowlist/denylist e bloquear IPs privados/link-local, inclusive em redirecionamentos.
4. **Travessia de diretório via `origem` do `copySound`** — `origem` era limpa com `/[^a-z0-9_.-]/gi`, que mantém o `.`; um valor como `../../package.json` sobrevivia até o caminho de leitura no repositório. Rejeitar nomes com `..` ou `/` e validar contra uma listagem conhecida de sons.
5. **Superfície de travessia no proxy `/sounds/`** — o `seguro` mantinha `.`, então `..` podia chegar ao construtor da URL raw; o escopo do GitHub raw limita o impacto, mas a entrada deveria rejeitar `..` mesmo assim.
6. **Corrida de lost-update / 409 no animals.json** — chamadas concorrentes de `saveAnimal` leem o mesmo `sha`, então uma sobrescreve a outra ou o GitHub retorna 409. Fazer retry em 409 relendo o arquivo e reaplicando, com laço limitado.
7. **Deploy hook dispara em toda escrita** — `dispararDeployFrontend()` roda após cada escrita bem-sucedida, então edições em lote enfileiram muitos redeploys. Considerar debounce ou disparar só quando o conteúdo realmente mudou.
8. **Respostas de erro colapsam para 400 e vazam detalhe interno** — falhas do GitHub/serviço externo retornavam como 400 com `err.message` cru. Mapear conflito/serviço externo/auth para códigos distintos e evitar ecoar detalhe interno.
9. **Sem testes automatizados** — nenhum dos sanitizadores, da proteção SSRF ou da lógica de merge de animais era coberto. Adicionar testes unitários para `sanitizarNome`, checagens de extensão, a rejeição de `..` e o read-modify-write de animais.

## Persistência como commits, e o custo disso

O `github-storage.mjs` trata o repositório como banco de dados: `putFile` faz GET do blob atual para pegar o `sha` e então faz PUT do novo conteúdo em base64, e `saveAnimal` faz um read-parse-merge-write completo de `src/assets/animals.json`.

O custo é que cada gesto do usuário é um commit, e o serviço guarda um `GITHUB_TOKEN` com escrita em Contents para fazê-los. Esse único fato eleva o risco de todas as outras preocupações aqui: um endpoint aberto não é um rabisco num disco que reseta no próximo deploy, é um push durável para `main` que também dispara um rebuild de produção.

## Sem auth, e CORS aberto por padrão

Não havia checagem de credencial em lugar nenhum do `index.mjs`. As quatro rotas de escrita eram alcançáveis por qualquer um que soubesse a URL. Combinado com `ALLOWED_ORIGIN` caindo para `*`, um navegador em qualquer origem podia fazer POST em `/api/download` ou `/api/animal`:

```js
const ALLOWED_ORIGIN = process.env.ALLOWED_ORIGIN || '*';
```

Como o backend grava no repositório sob o próprio token, isso era, na prática, um endpoint de escrita-para-`main` não autenticado mais um gatilho de redeploy. No mínimo, as rotas de escrita precisam de um header com segredo compartilhado comparado em tempo constante, e `ALLOWED_ORIGIN` deveria falhar fechado (recusar escritas) quando não definida em produção, em vez de cair para `*`.

## SSRF no /api/download

`downloadSound(url, nome)` validava apenas que a URL faz parse, é http(s) e não é YouTube, e então fazia fetch server-side com redirects seguidos:

```js
if (!/^https?:$/.test(parsed.protocol)) throw new Error('Use uma URL http(s).');
...
resposta = await fetch(url, { redirect: 'follow' });
```

Nada bloqueava `http://169.254.169.254/latest/meta-data/...`, `http://localhost:<porta>/...` ou hosts RFC-1918. No Render a superfície interna/metadados pode ser limitada, mas o padrão é um SSRF de manual: quem chama (não autenticado) faz o servidor emitir requisições de saída arbitrárias para hosts à escolha dele, e `redirect: 'follow'` significa que uma URL pública permitida pode dar 302 para uma interna. A correção resolve o hostname, rejeita faixas privadas/link-local/loopback antes de conectar e revalida após cada redirect (ou desabilita redirects e valida salto a salto). A resposta é commitada no repositório, então isso também vira uma forma de escrever bytes arbitrários (até 15 MB) controlados por quem ataca em `src/assets/sounds/`.

## Sanitização de nomes deixava `..` vivo em dois caminhos

`sanitizarNome` (usada para o id de destino) é sólida: reduz a `[a-z0-9_-]` após normalização NFD, então o nome de destino não trava. Mas duas entradas usavam um filtro mais fraco que mantinha o ponto:

```js
// copySound
const origem = String(origemArquivo || '').replace(/[^a-z0-9_.-]/gi, '');
// handler /sounds/
const seguro = nomeArquivo.replace(/[^a-z0-9_.-]/gi, '');
```

`..` e `.` sobreviviam nos dois. Em `copySound`, `origem` fluía para `getFile(`${SOUNDS_PREFIX}/${origem}`)`, então `../../package.json` podia escapar do prefixo de sons no lado da leitura. Ambos deveriam rejeitar qualquer valor contendo `..` ou `/`, e `copySound` idealmente valida `origem` contra `listSounds()`.

## Escritas concorrentes no animals.json

`saveAnimal` é um read-modify-write contra um único arquivo. `putFile` relê o arquivo para anexar o `sha` mais recente, mas ainda há uma janela: duas requisições que leem o mesmo `sha` competem. Um PUT vence; o segundo ou sobrescreve o primeiro animal ou o GitHub rejeita com 409. A correção é um laço de retry limitado: no 409, reler `animals.json`, reaplicar o merge e dar PUT de novo.

## Deploy hook dispara em toda escrita bem-sucedida

Criar um animal na UI faz uma escrita de som e uma de animal — dois commits, duas chamadas de hook, potencialmente dois redeploys empilhados. Nada aqui está quebrado, mas no plano gratuito isso multiplica minutos de build. Debounce do hook cortaria rebuilds redundantes.

## Tratamento de erro achatava tudo para 400

Toda rota de escrita envolvia o handler num try/catch que retornava `sendJson(res, 400, ...)`. Um 409 do GitHub, um 403 de rate-limit, um 5xx de serviço externo no `/api/download` e entrada genuinamente inválida vinham todos iguais como HTTP 400 com a mensagem interna crua. Códigos distintos (409 para conflito, 502 para serviço externo, 400 só para validação) e uma mensagem sanitizada ao cliente seriam uma melhoria significativa.

## Integração do frontend e a cadeia de fallback

`sound-server.ts` centraliza a seleção de URL atrás de uma constante `SOUND_SERVER` e uma flag `EH_LOCALHOST`, com um override em runtime `window.__SOUND_SERVER__`. `jardim.component.ts` usa isso para um fallback de áudio em três passos: asset empacotado, depois `${SOUND_SERVER}/sounds/<id>.mp3`, depois o oscilador sintetizado.

Uma assimetria de comportamento, documentada no código como intencional: em produção o handler de arrastar-para-reposicionar pula a escrita no servidor (`if (!EH_LOCALHOST) return;`) e mantém posições só no `localStorage`, então posições de animais são por navegador em produção. Não é bug, mas significa que um jardim reposicionado fica diferente em cada dispositivo.

## Situação após as correções (commit 39f19e7)

Todas as questões de segurança e concorrência de maior prioridade foram corrigidas e validadas (build, testes e checagens em produção):

1. **Autenticação de escrita** — adicionada via `WRITE_SECRET` opcional (header `x-write-secret`, comparação em tempo constante). Fica desligada se a variável não for definida, para compatibilidade.
2. **CORS fail closed** — sem `ALLOWED_ORIGIN`, nenhuma origem externa é liberada (não cai mais para `*`).
3. **SSRF** — `downloadSound` agora resolve o host e recusa IPs internos (loopback, privados, link-local/metadados), revalidando a cada redirecionamento (seguidos manualmente).
4. **Travessia em `copySound`** — usa `nomeArquivoSeguro` (rejeita `..`, `/`, `\`) e valida a origem contra `listSounds()`.
5. **Travessia no `/sounds/`** — usa `nomeArquivoSeguro`; entradas com `..` retornam 400.
6. **Corrida no animals.json** — laço de retry em 409 (relê e reaplica o merge).
7. **Deploy hook por escrita** — mantido como está (aceitável para app de um usuário); anotado como melhoria futura (debounce).
8. **Códigos de erro** — `AppError` com status (400/401/409/502); o servidor responde com o código certo.
9. **Testes** — `server/github-storage.test.mjs` (`node --test`) cobre sanitização, rejeição de travessia e detecção de IP interno.
